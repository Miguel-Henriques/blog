## Principle

Permission to crawl is not the same as being agent-ready.

This site is a public CV and project portfolio. Default to open access.
Invest effort in machine-readable guidance and facts, not in enumerating
bot names in `robots.txt`.

## Stack

| Layer | File / surface | Job |
| --- | --- | --- |
| Access | `/robots.txt` | Who may crawl |
| Discovery | `/sitemap.xml` | Which URLs exist |
| Guidance | `/llms.txt` | What the site is and what to read first |
| Facts | structured JSON / page content | Reliable citations |

`robots.txt` controls access. `llms.txt` guides comprehension. Neither
replaces the other.

## robots.txt

Keep it minimal. Production already allows everything and points at the
sitemap via `scripts/finalize-build.mjs`.

Target shape:

```txt
# Portfolio of Miguel Pestana Henriques — CV, experience, and projects.
# Prefer /llms.txt for LLM/agent context.

User-agent: *
Allow: /

Sitemap: https://YOUR_DOMAIN/sitemap.xml
```

Do:

- Keep `User-agent: *` + `Allow: /`
- Always emit `Sitemap:` with the real `SITE_URL`
- Optionally comment-point agents at `/llms.txt`

Do not:

- List every AI bot with redundant `Allow: /` (already covered by `*`)
- Add `Crawl-delay`
- Disallow public assets needed for the portfolio (certs, speaking media)

If a CDN (for example Cloudflare) sits in front later, check its AI-crawler
defaults separately. Those can block bots even when `robots.txt` allows them.

Only add per-bot `Disallow` rules if you deliberately want to opt out of
training or citation for a specific crawler.

## sitemap.xml

Keep the sitemap accurate and small.

Today the build emits a single URL (`/`). That is enough for a one-page
portfolio. When routes or public machine files are added (for example
`/llms.txt` or a public profile JSON), include them if they should be
discovered by crawlers.

## llms.txt

Highest-leverage file for this site. Serve Markdown at `/llms.txt`.

Goals:

- State who you are and what the site contains in two sentences
- Point agents at the CV/home page, GitHub, LinkedIn, and any structured
  facts endpoint
- Keep it curated, not exhaustive

Example:

```md
# Miguel Pestana Henriques
> Software engineer in Lisbon. Portfolio covering CV, experience
> (AWS, Contextual, Deloitte), and personal GitHub projects.

## Primary
- [Home / CV](https://YOUR_DOMAIN/): Full portfolio and experience
- [GitHub](https://github.com/Miguel-Henriques): Personal projects
- [LinkedIn](https://www.linkedin.com/in/miguelhenriques96): Professional profile

## Optional
- [profile.json](https://YOUR_DOMAIN/profile.json): Structured CV data
```

Write factual descriptions. Avoid marketing language. Update when role,
projects, or canonical links change.

`llms.txt` does not grant or deny access. Access still comes from
`robots.txt` and any CDN rules.

## Structured facts

`content/profile.json` is already the source of truth for the CV UI.

To make agents cite you reliably:

1. Expose a stable public facts file (for example `/profile.json`) generated
   or copied at build time from `content/profile.json`
2. Link that file from `/llms.txt`
3. Keep human page copy aligned with the JSON so agents do not see
   conflicting summaries

Optional later: Person/Profile JSON-LD on the homepage. Useful, but
secondary to `llms.txt` plus a public facts file.

## What to skip

- Treating `robots.txt` as the main agent-readiness work
- Shipping `ai.txt` unless you care about training/licensing signals
- `llms-full.txt` until there is enough content that a full dump helps
- Blocking AI crawlers by default on a public portfolio meant to be found

## Build integration

Wire agent files into `scripts/finalize-build.mjs` next to the existing
`sitemap.xml` / `robots.txt` generation so they:

- Use the same `SITE_URL`
- Stay in sync with `content/profile.json`
- Ship only on real deploys, not as stale hand-edited public stubs
